# V2-12.5 — Storage, Email, Observability, and Incident Readiness

Status: `DEFERRED — EXTERNAL INSTITUTIONAL DEPENDENCY / POST-HANDOFF`

## Scope

This subphase owns provider-readiness controls for private document storage and
transactional email, redacted operational logging, liveness monitoring, alert
inputs, and incident playbooks. It excludes a Production deployment, provider
activation, live email, database migration, backup/restore, and V2-12.6 final
hardening or handoff.

## Acceptance criteria

1. Storage and email configuration fail closed and can be checked without
   exposing values or contacting providers.
2. Private document delivery remains private; the test-memory driver is rejected
   from a Production-ready provider configuration.
3. Scheduled email dispatch is protected, bounded, and uses the existing
   idempotent outbox rather than a browser-accessible endpoint.
4. Liveness and operational records expose no private data, secrets, provider
   values, or internal configuration details.
5. Monitoring, alert inputs, incident containment, recovery, and ownership
   procedures are documented.
6. Provider activation dependencies are recorded as owner-controlled external
   actions, without claiming they occurred.

## Repository-controlled evidence

- Provider readiness requires a non-empty Blob identity, `RESEND_API_KEY`, a
  syntactically valid `EMAIL_FROM`, and a `CRON_SECRET` of at least 32
  characters; it rejects test-memory storage and returns categories only.
- The protected scheduler compares the bearer secret in constant time and fails
  closed for absent or short values. The application cannot prove a value's
  random origin; operations require generation with a cryptographically secure
  random generator.
- Private downloads remain authenticated and return generic failures; liveness
  and operational records do not reveal provider values, private identifiers,
  exception payloads, or configuration state.
- Fast-close verification passed: 7 focused Vitest files / 15 tests, changed
  file Prettier, repository ESLint, strict TypeScript, Prisma validation,
  synthetic non-network Preview/Production/provider verifiers, and the 31-page
  production build. No verifier contacted a provider or database.
- Preview deployment is Ready. Preview and Production Resend API keys and
  scheduler secrets are separate. The Preview key was rotated; a direct Resend
  synthetic smoke with the new Preview key returned an email ID. UptimeRobot
  monitors Preview every five minutes, reports Up, and its email alert was
  tested. These are owner-reported external facts, not repository checks.

## Deferred external institutional dependency

The current Cloudflare account has no access to the existing `sist.ac.ma` DNS
zone. An authorized institutional DNS owner must install the Resend DNS records
for `updates.sist.ac.ma` in that zone and wait for Resend verification. This
must not be bypassed by creating a duplicate zone or by treating the Preview
`onboarding@resend.dev` sender as an institutional domain. This does not block
Monday demo/handoff preparation; arbitrary production email sending remains
disabled until verification is recorded after handoff.

Production release remains deferred by owner and is not a V2-12.5 action.
