## V2-12.1 governance plan

### Environment model

| Environment | Boundary and permitted use                                                                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Local       | Developer-owned; local or isolated test database only; local-only credentials, safe substitutes, and no Production data.                                                 |
| Preview     | Vercel Preview or approved equivalent; isolated Preview database and secrets; sanitized/test data only; release-candidate verification.                                  |
| Production  | Human-approved release only; Production-only database and secrets; no destructive testing; restricted operational ownership, recorded deployment, and rollback evidence. |

Promotion is Local → Preview → an approved Production release commit. Preview and Production must never share a database or secret scope.

### Secret governance

The current example/environment code identifies `APP_URL`, `DATABASE_URL`, `DIRECT_URL`, `TEST_DATABASE_URL`, `AUTH_SECRET`, document-storage settings, and development seed controls. Storage code also requires a Vercel Blob token or store identity; email code requires a Resend API key and sender address. These names/categories are documentation only, never values.

- Secrets are scoped separately for Local, Preview, and Production and remain outside Git, logs, reports, screenshots, and test artifacts.
- Startup/build validation must fail safely with field-only configuration errors; values must never be reported.
- A designated secret custodian and rotation owner must maintain inventory, access control, routine rotation, and emergency revocation/replacement.
- Emergency rotation requires containment, replacement in the affected scope, application/release verification, access review, and sanitized incident evidence.

### Git and release governance

- Production may be released only from an approved, reviewed commit with a clean synchronized branch and recorded verification evidence.
- Human Production approval is mandatory. Force pushes and history rewrites are prohibited for release history.
- Release evidence records the commit, reviewer/approver, checks, environment, migration decision, deployment result, and rollback reference.
- Rollback uses an identified previously approved release commit or provider release reference; a forward fix is preferred when database state makes code rollback unsafe.

### Vercel plan

Preview deployments must use Preview-only variables, an isolated Preview database, and a verified approved commit. Production deployment requires the same separation, explicit human approval, recorded release evidence, and a known rollback reference. No Vercel project, connection, or deployment is created by V2-12.1.

### Database operations plan

Local, Preview, and Production databases remain separate. Checked-in reviewed Prisma migrations are the only production schema path; `prisma db push`, reset, and destructive production testing are prohibited. A future release runbook must assign migration ownership, require review and approval, take/verify a pre-deployment backup, rehearse restoration in an isolated environment, verify after migration, and record the rollback-versus-forward-fix decision.

### Storage and email plan

Document artifacts currently use a private Vercel Blob abstraction, bounded to 5 MiB and served through authenticated download paths. Test execution can use an in-memory storage driver only under its explicit test-only guard. Production storage provider/account, credential ownership, retention, and recovery remain unresolved.

Notifications use a provider-neutral interface with a Resend implementation, a fake test provider, transactionally claimed delivery rows, idempotency keys, five attempts, exponential retry, and terminal failure state. Production email provider/account, sender domain, credential custodian, and operational delivery worker/schedule remain unresolved. Private attachments and personal data must not be exposed through provider URLs, logs, or notification content.
